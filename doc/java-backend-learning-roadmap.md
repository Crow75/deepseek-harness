# Java 后端开发者的 DeepSeek Harness 学习路线

## 概述

这份路线面向熟悉 Java、Spring Boot、HTTP 接口和数据库开发，但尚未系统使用 TypeScript 或开发 AI Agent 的工程师。学习目标是能够解释一次任务的完整执行过程、定位相关插件，并独立完成一个有验证证据的小改动。

建议每天投入 1～2 小时，用四周完成主线；时间安排是学习建议，可以按阶段验收结果调整。先运行和观察，再阅读实现，最后扩展能力。无需一开始通读全部包、研究模型训练或深入前端与原生模块。

本文按要求放在 `doc/`；项目正式文档位于 `docs/`。安装、启动和配置操作以链接中的维护文档为准，本路线主要安排学习顺序和练习。

## 先建立项目认识

DeepSeek Harness 是一个由 Cordis 驱动的插件化智能体框架。模型适配、工具注册、会话日志和 Agent 执行循环本身都通过插件组成。学习重点是这些能力如何协作，而非只寻找传统 Web 项目的 Controller、Service 和 DAO。

先区分四个概念：Agent 是运行中的智能体；Session 是可记录和恢复的会话；step 是一次模型请求及其工具调用；turn 包含零个或多个 step。模型选择调用工具后，工具结果会参与后续请求，因此一次用户输入可能触发多次模型请求。

第一遍只建立以下关系，具体顺序和异常分支在第二周展开：

```text
启动入口与 profile → Cordis 插件树 → 服务与事件
用户输入 → Agent → 组装模型请求 → 模型响应
                                ↓
                           工具调用与结果
                                ↓
                           后续模型请求

Session 日志记录持久事实，并用于推导模型历史；
实时流事件用于呈现尚在生成中的内容。
```

阅读入口：[项目介绍](../README.zh.md)、[架构](../docs/architecture.zh.md)、[包分组地图](../packages/README.zh.md)。完成后，用自己的话解释“为什么模型适配器、工具和执行循环可以分别替换”。

## 把 Java 经验迁移过来

以下对照帮助理解职责，不能视为运行机制完全相同。

| Java 后端经验 | 本项目中的学习对象 | 需要调整的认识 |
|---|---|---|
| Maven 多模块 | pnpm workspace 与 `packages/<group>/<package>` | 先看包依赖和公开入口，再看内部文件；跨包使用包名导入 |
| Spring IoC 与依赖注入 | Cordis `Context`、服务与 `inject` | 服务通过 `ctx` 使用，插件依赖由框架管理；同时学习作用域与卸载 |
| Bean 生命周期与资源销毁 | `ctx.effect()`、`ctx.on()` 与 disposer | 注册和监听需要随插件生命周期撤销 |
| 接口与多种实现 | Service Definition、Service Provider、Consumer | 学习完整调用关系，区分接口、实现者和使用者 |
| 拦截器与环绕通知 | waterfall 事件 | 调用 `next()` 才会委托后续监听器，不调用会短路 |
| DTO 与泛型 | TypeScript interface、泛型、联合类型 | 类型在运行时擦除；外部 JSON 和配置仍需校验 |
| 枚举分支处理 | 带判别字段的联合类型 | 根据标签缩小类型，封闭联合要求完整处理分支 |
| CompletableFuture 与异步任务 | Promise、async/await、异步迭代器 | 理解事件循环、流式消费、取消和清理，避免阻塞式思维 |
| 业务事件与审计记录 | 运行时事件与持久 Session 事件 | 运行时通知与可恢复记录职责不同，不能互相替代 |
| JUnit 与集成测试 | Vitest、expected、snapshot 与 e2e | 根据修改影响选择证据；真实 API 测试与无密钥回放各有用途 |

## 四周安排

每个阶段都应留下可检查的产出。阅读量不是完成标准；能解释机制、找到代码并验证行为才是。

| 时间 | 重点 | 阶段产出 |
|---|---|---|
| 第 1 周前半 | 环境、产品体验、TypeScript 必要基础 | 一份本地运行记录和语言概念对照 |
| 第 1 周后半 | Cordis 服务、事件、effect 与配置 | 一个教程练习及插件依赖关系图 |
| 第 2 周前半 | Agent、turn、step 与模型请求 | 一张含源码入口的执行时序图 |
| 第 2 周后半 | 工具注册、调用、结果与后续请求 | 一份工具调用链分析 |
| 第 3 周前半 | Session 日志、投影与持久化 | 一份会话恢复分析 |
| 第 3 周后半 | Shell、子进程、取消与错误处理 | 一份失败场景和责任归属记录 |
| 第 4 周 | 小型插件或局部修复、文档与验证 | 一个范围清楚、可评审的改动 |

## 第一周：运行项目与掌握插件基础

这一周先建立可用的开发环境，再用小练习理解框架。遇到环境问题时先记录实际错误，依据开发指南解决，不要通过绕开正式入口来启动应用。

### 1. 环境与产品体验

阅读[安全说明](../SAFETY.zh.md)和[开发指南](../docs/development.zh.md)，按指南准备 Node.js、pnpm 和构建环境。版本要求查根目录 [package.json](../package.json) 的 `engines` 与 `packageManager`，不要沿用其他项目的版本习惯。

按[源码运行说明](../README.zh.md#run-from-source)体验 Web 应用，记录启动入口、profile、配置来源和日志位置。涉及真实模型时，按[测试文档](../docs/testing.zh.md)确认 API 密钥要求；没有密钥时先完成 Cordis 教程与代码阅读，将真实请求体验留作后续练习。

验收：能够说明源码、构建产物和运行配置分别在哪里；能区分构建问题、插件加载问题和模型访问问题。

### 2. 补齐必要的 TypeScript 与 Node.js 知识

只补阅读本项目必需的知识：ESM 导入导出、`import type`、interface、泛型、联合类型、类型缩小、声明合并、Promise、异步迭代器与 `AbortSignal`。可从 [Cordis 教程的 TypeScript 说明](../docs/cordis-tutorial/index.zh.md#typescript-notes)开始，再结合源码学习。

练习：找到一个带判别字段的联合类型，解释各分支；找到一个 `declare module`，指出它扩展了什么类型；找到一个异步函数，标注它在哪些位置等待外部工作。

验收：能够解释“声明合并增加类型信息，但不会自动提供运行时服务”，以及“TypeScript 类型检查不能代替对外部输入的校验”。

### 3. 掌握 Cordis 插件组合

阅读[Cordis 入门](../docs/cordis-primer.zh.md)，按[Cordis 教程](../docs/cordis-tutorial/index.zh.md)依次练习插件、生命周期、服务、事件和配置。随后阅读[第一个 Harness 插件](../docs/user/develop/basic/index.zh.md)，将教程概念连接到真实应用。

重点回答：插件依赖如何声明？服务何时可用？谁拥有监听器和注册项？卸载后如何撤销？waterfall 监听器什么时候应该调用 `next()`？profile、bundle 与 patch 如何参与组合？

验收：画出一个插件的依赖、注册和清理关系；能指出业务能力应该接入哪个服务或事件，而不是直接修改执行循环。

## 第二周：追踪 Agent 执行与工具调用

这一周围绕一次任务阅读源码。先看公开接口，再追主路径，最后看异常分支；暂时不展开每个 provider 的实现。

### 4. 追踪一次 turn

阅读[架构](../docs/architecture.zh.md)、[Agent 生命周期](../docs/agent-lifecycle.zh.md)和 [agent-loop README](../packages/core/agent-loop/README.zh.md)。按以下顺序定位职责：

1. [Agent 类型](../packages/core/agent/src/types.ts)：调用方能创建、输入和控制什么。
2. [agent-loop 入口](../packages/core/agent-loop/src/index.ts)：默认循环如何作为插件接入。
3. [Agent 实现](../packages/core/agent-loop/src/agent.ts)：输入、turn、step 与请求准备如何协作。
4. [LLM 类型](../packages/llm/llm/src/types.ts)：循环和模型适配器交换什么数据。

练习：以“用户要求读取一个文件并总结内容”为案例，画出输入、请求准备、流式响应、工具调用、工具结果和下一步请求。标注哪些节点是运行时事件，哪些事实需要持久记录。

验收：能够解释 turn 与 step 的区别、工具结果为何可能引发下一次请求，以及一次失败或取消应到哪里继续追踪。

### 5. 追踪一个工具

阅读[工具执行流水线](../docs/tool-execution-pipeline.zh.md)和[添加工具指南](../docs/cookbook/adding-a-tool.zh.md)，从 [tools 包](../packages/core/tools/README.zh.md)找到注册与执行流程，再选择一个具体工具。Windows 可从 [pwsh 工具](../packages/shell/tool-pwsh/README.zh.md)开始。

跟踪顺序：工具定义与参数 schema → 注册与作用域 → 请求中的工具声明 → 模型返回调用 → 执行前处理 → provider 执行 → 结果记录 → 后续模型历史。

练习：写下工具名称、参数来源、执行服务、错误由谁处理、结果如何呈现。将工具消费者与底层执行器分开画，说明替换执行器时哪些代码应该保持独立。

验收：能够定位参数校验、执行拦截和结果生成的位置；知道新增能力前需要同时考虑模型输出、用户呈现和测试。

## 第三周：理解 Session 与后端能力

这一周利用已有的数据库和后台任务经验，理解可恢复记录、异步资源以及故障处理。先理解记录与读取，再研究物理存储和迁移。

### 6. 理解 Session 与模型历史

阅读 [Session 包](../packages/core/session/README.zh.md)、[Session 子系统](../docs/subsystems/session.zh.md)、[持久化接口](../packages/session/session-persistence/README.zh.md)和 [JSONL 实现](../packages/session/session-persistence-jsonl/README.zh.md)。源码入口为 [Session 类型](../packages/core/session/src/types.ts)和 [Session 实现](../packages/core/session/src/index.ts)，重点寻找 `deriveMessages()`。

理解 Session 日志如何推导模型历史，以及实时生成内容与最终提交记录的关系。不要把所有日志都当作可直接发送给模型的聊天消息；失败尝试和运行状态也有各自的记录用途。

练习：选择一个已有会话或记录回放，区分用户消息、助手消息、工具调用与结果；再解释这些记录如何支撑恢复与展示。涉及格式演进时查看[Session 格式状态](../docs/session-format-status.md)和[持久化类型变更审查](../docs/cookbook/reviewing-persistence-type-changes.md)。

验收：能够说明为何模型可见输入需要可从日志重建；区分内存中的逻辑事件与磁盘上的存储格式；知道修改持久类型前必须查兼容性要求。

### 7. 理解执行器、取消与错误处理

阅读 [Shell 能力家族](../packages/shell/README.zh.md)、[子进程能力家族](../packages/subprocess/README.zh.md)、[防御性模式](../docs/defensive-patterns.zh.md)及[错误处理规范](../.agents/skills/dsh-error-handling/SKILL.md)。重点理解请求解析、执行、后台句柄、取消和资源清理的归属。

练习：分析“命令执行失败”“模型请求取消”“插件卸载时任务仍在运行”三个场景。分别记录谁发出取消、谁释放资源、会话记录什么，以及用户或调用方如何得知失败。

验收：能够区分失败、取消和执行结果未知；能说明为什么 Node.js 异步代码仍然需要防范竞态，以及清理工作为何必须明确资源所有者。

## 第四周：完成一个小型贡献

这一周选择一个能够独立验证的任务，将框架理解转化为实际开发。范围以一个能力或一个明确行为为宜。

### 8. 选择练习并形成可评审改动

推荐实现一个只读取学习资料目录、返回匹配文件路径的小工具。先定义用途、参数、允许读取的目录、结果格式和失败报告，再依据[添加工具指南](../docs/cookbook/adding-a-tool.zh.md)接入现有能力；运行组合使用正式 profile 与 patch 路径。

如果环境暂时不具备运行插件的条件，可以选择现有插件中一个可复现的小问题，或补充一条缺失的行为测试。选择前先确认该能力是否已经存在，避免重复实现。

按以下步骤完成：

1. 阅读根目录与目标目录的 `AGENTS.md`，确认接口、文档和测试要求。
2. 找到相近实现，明确需要新增还是复用；写下正常输入与失败输入的预期行为。
3. 完成最小实现和对应 README、JSDoc；涉及外部可感知的破坏性变更时同步升级指南。
4. 根据[测试策略](../docs/testing.zh.md)选择行为测试、expected、记录回放或真实 API 验证。非平凡的模型或产品可见变更需要更新所属快照。
5. 按[推送前检查规范](../.agents/skills/dsh-pre-push-checks/SKILL.md)选择与改动相关的检查，记录实际执行结果与未验证项。
6. 写一份简短评审说明：解决什么问题、调用方看到什么行为、如何验证、还有什么限制。

验收：其他开发者能够根据你的说明复现行为；改动不依赖绕过应用入口，不将插件能力直接写入循环，也不遗漏错误、资源清理和可见输出的验证。

## 源码阅读方法

每次只追踪一个问题。例如“工具结果从哪里进入下一次模型请求”，不要同时阅读启动、前端、持久化和所有模型 provider。

采用“README → 公开类型 → 注册入口 → 核心实现 → 对应测试”的顺序。包 README 解释用途与限制，类型说明调用约定，入口展示插件接线，测试帮助确认正常和异常行为。

每次阅读留下四项记录：入口文件与关键符号、输入输出、依赖的服务或事件、对应测试。没有阅读依据的判断标为待确认，不把猜测写成项目事实。

调试时先找最小场景和现有测试，围绕输入接收、请求准备、工具执行、Session 提交设置观察点。先验证主路径，再增加取消、错误或恢复情形。

## 容易走错的方向

| 容易采用的做法 | 建议的学习方式 |
|---|---|
| 按目录逐个通读全部包 | 围绕一次请求建立调用链，按依赖扩展阅读 |
| 将 Cordis 当成另一套 Spring 注解容器 | 同时学习服务依赖、作用域、事件模式和可逆 effect |
| 先修改 agent-loop 来加入业务能力 | 先查已有服务和事件扩展点，确定能力归属 |
| 将 Session 当成普通聊天表 | 学习事件日志、模型历史推导、恢复和格式兼容性 |
| 用类型断言代替输入校验 | 区分静态类型保证与 JSON、配置、持久数据的运行时校验 |
| 每次改动都运行全部检查 | 按影响范围选择检查，并保留实际执行证据 |
| 一开始深入 Electron、原生模块或全部 UI | 完成后端主线后，再按工作目标选择专题 |

## 最终验收清单

- [ ] 能区分运行时事件、Session 事件和模型历史。
- [ ] 能追踪一个工具的参数、执行服务、结果与错误处理。
- [ ] 能解释 Session 恢复与持久数据兼容性需要关注什么。
- [ ] 能分析取消与资源清理的责任归属。
- [ ] 能完成一个小改动，并提供文档和与影响范围匹配的验证证据。
